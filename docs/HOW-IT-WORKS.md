# How it works

All addresses are for `enshrouded_server.exe` of Steam build 25988414 (TimeDateStamp
1792148062, SizeOfImage 0x1dcf000, image base 0x140000000). RVA = address − 0x140000000.

Build 26083076 (20 October 2026) has the same code at each site; only the addresses moved (see
`tools/selftest.cpp` for both builds). Three patterns carry wildcards for call targets and
rip-relative displacements, and the add helper is resolved through the call the two XP systems make.

## Loading

The server imports `POWRPROF.dll`, which is not a KnownDLL, so Windows (and Wine with
`WINEDLLOVERRIDES=powrprof=n,b`) loads the copy next to the exe first. The mod exports all
139 functions of the real library; each export is a stub that jumps to the real function in
`System32\powrprof.dll` (`src/proxy.cpp`, stubs generated by `tools/gen_proxy.py`).

`DllMain` starts one thread that reads `xpshare.ini`, checks the build stamp, finds every hook
site by a byte pattern that must match exactly once in `.text` (`src/scan.cpp`) and installs
the hooks with SafetyHook mid-function hooks (`src/hooks.cpp`). If anything does not match,
nothing is hooked and the server runs unmodded.

## XP model in 1.0

Each player has an experience component with a "pending XP" field (field hash `0x1d7dd102`).
XP sources add to that field; once per tick the experience system reads it, commits it to the
player's XP, handles level-ups and syncs the result to the client. Every gain carries an
ExperienceSourceType: 1 Exploration, 2 Lore, 3 Quest, 4 Combat, 5 Mining, 6 ItemSetCompleted.

## Hook sites

| Hook | RVA | Instruction | What it reads |
|---|---|---|---|
| `mining` | 0x226cbc | `add [rcx+rdx*4], r15d` in FUN_140226c40 | amount `r15d`, entity id at `[rbp+0x14c]` |
| `knowledge` | 0x1b566a | `add [rcx+rdx*4], edi` in FUN_1401b5490 | amount `edi`, type `byte [r15]`, entity id `*[rbp+0x6f]` |
| `add_helper` | 0x1950f0 | entry of the "add to field" helper FUN_1401950f0 | amount `r8d`, field hash `r9d`, caller from the return address |
| `commit_read` | 0xcf018 | `mov r15d, [rcx+rdx*4]` in the experience system FUN_1400cedd0 | pending XP at `rcx+rdx*4`, entity id via the system parameter at `[rbp+0x130]` |

`add_helper` only counts pending-XP adds (`r9d == 0x1d7dd102`) from two known callers, the
knowledge systems FUN_1401b7530 (type at `[rsp+0x80]` on entry, entity id `[r15]`) and
FUN_1401b67a0 (type at `[rbp-0x60]`, entity id `[rbp+0xa0]`). Their return addresses
(RVA 0x1b77e1 and 0x1b6a7a) are found by pattern too. Other callers are logged once and
ignored.

| `combat` | 0xecbce | `add [r8+r9*4], r15d` in the combat system FUN_1400ec5c0 | amount `r15d`, receiver entity id `edi`, receiver index `r12`, kill record `[rsp+0x48]` |

The combat hook is only installed with `ShareCombatXp=1`. For every kill the combat system
collects the receivers near it (list at `[rbp-0x80]`, count at `[rbp-0x78]`) and gives each
of them XP from FUN_14092ac40: the kill's XP value, scaled by the level difference between
enemy and receiver and lowered for every extra receiver. The hook numbers the kills: a new
kill starts when the kill record changes or the receiver index does not grow.

Players are identified by entity id, the number the game writes into every XP event. The
experience component's address is not stable (it moves on fast travel, for example).

## Sharing

`src/ledger.cpp` is plain logic without game code and has unit tests
(`tests/ledger_test.cpp`):

1. The source hooks record each gain with the entity id of the player who earned it (combat
   gains also with the number of their kill).
2. The `commit_read` hook runs once per player per tick. It adds to that player's pending XP
   the sum of all gains other players recorded since that player's previous visit, times
   `Multiplier`. The game then commits it like any other XP, including level-ups and sync.
3. A player seen for the first time gets nothing for the past. Gains and players not seen
   for 120 seconds are dropped.
4. Joint quests (`DoubleQuestXp=0`, the default): there is no quest id in the XP event, so a
   quest gain from another player is skipped for a receiver who recorded a quest gain of the
   same amount within 10 seconds of it (`kJointWindowMs`). Quest gains are held 5 seconds
   (`kQuestHoldMs`) before they are shared, so the receiver's own gain has time to arrive; a
   receiver's later gains wait behind a held quest gain, they are delayed, never lost.
5. Combat (`ShareCombatXp=1`): combat gains are held 1 second (`kCombatHoldMs`) so every gain
   of a kill is in. A kill is settled once, at its first gain: a receiver who got XP from it
   gets nothing more; every other player gets the largest amount any player got from it.

All game memory reads go through SEH-guarded helpers (`src/memory.cpp`), so a bad pointer
skips one gain instead of crashing the server.

## After a game update

1. Build and run `build\xpshare_selftest.exe <new enshrouded_server.exe>`.
2. If it says `unknown server build` but the patterns still match uniquely on the new exe, the
   code around the hooks may still be the same; verify each site in a disassembler before
   changing `kTimeDateStamp` and `kSizeOfImage` in `src/scan.cpp`.
3. If a pattern matches 0 or more than 1 times, find the site again (the functions above,
   searched by their instruction sequences) and update the pattern, offset and the frame
   offsets in `src/hooks.cpp`.
4. Test on a test server with two players and `LogEveryShare=1` before releasing.
